# Upgrading from 0.3 to 0.4

0.4 adds NestJS 12 support and a set of opt-in improvements. The only
requirement is **Vite 7 or newer**. An application on 0.3.x that meets it,
upgrades and changes nothing else keeps rendering the same pages, with the same
responses, on NestJS 11 or 12.

```bash
pnpm add @nestjs-ssr/react@^0.4.0
```

## Vite 7 or newer

Vite 6 is no longer supported (peer range `^7 || ^8`). The per-route client
entry waits for the page's code with a top-level `await`, which Vite 6's default
build target rejects. If you are on Vite 6, upgrade Vite and
`@vitejs/plugin-react` first; nothing in this library's configuration changes.

## NestJS 12

Both NestJS 11 and 12 are supported (`@nestjs/*` peer range `^11 || ^12`).
Upgrade Nest on your own schedule; the library works the same on both.

Nest 12's `nest new` creates ES module projects (`"type": "module"`). They work
out of the box, and `init` generates ESM-correct files for them. In an ES module
project, relative imports in your own code need the `.js` extension:

```ts
import Home from './views/home.js';
```

## Optional: load each page's code separately

By default every view is bundled into the client entry, so every page downloads
every other page's code. New projects now load views per route, and the server
preloads the current page's chunk so hydration is not delayed. On an app with
30 more pages, a page's initial JavaScript went from 605 KB to 238 KB
(95 KB to 75 KB gzipped) — see [Performance](/performance).

To opt in on an existing project:

1. Add the Vite plugin. It lets the client and server find a page's module by
   its component name, whatever the file is called, and keeps those names
   through minification:

   ```ts
   // vite.config.ts
   import { nestjsSsr } from '@nestjs-ssr/react/vite';

   export default defineConfig({
     plugins: [react(), nestjsSsr()],
     // ...
   });
   ```

2. Replace `src/views/entry-client.tsx` with the current template:

   ```bash
   cp node_modules/@nestjs-ssr/react/src/templates/entry-client.tsx src/views/entry-client.tsx
   ```

   The only change is how views are discovered: `import.meta.glob(..., { eager: false })`
   plus `loadViewModules()` for the rendered page and its layouts.

Keep the old entry-client and nothing changes: the server only adds preload
tags when the client entry loads views lazily.

## Optional: no restarts when you edit a view

`nest start --watch` restarts Nest on every compile, and every view edit
compiles. `nestjs-ssr dev` restarts only when something outside `views`
changes; view edits appear through Vite without a restart (0.13–0.2 s instead
of a full reboot on the example app). Swap your `dev:nest` script:

```json
{
  "scripts": {
    "dev:nest": "NODE_ENV=development nestjs-ssr dev --watchAssets"
  }
}
```

The server finds an edited view by its component name, so file names do not
have to follow the component (`SpecialsList` in `recipe-list.tsx` is fine).

Monorepos with several Nest projects should keep `nest start <project> --watch`
for now.

## Optional: error pages in string mode

When a page throws while rendering in string mode, the error has always gone
to Nest's exception filters (a JSON 500 by default). Set `showErrorPage` to
answer with an error page instead: in development it shows the error, the
failing source lines and a source-mapped stack; in production it is the generic
error page with no details.

```ts
RenderModule.forRoot({ showErrorPage: true });
```

Leave it off if your own exception filter handles render errors.

## Fixes you get automatically

- **Catch-all routes** (a 404 page, an SPA fallback such as `@Get('*path')`)
  answered for every built asset in production and every Vite module request
  in development, because static serving and the Vite proxy were registered
  after the application's routes. They now run ahead of the routes.
- **Graceful shutdown dropped requests in flight.** Every shutdown closed all
  open connections, including requests still being answered, so a rolling
  deploy cut responses off. Production shutdowns now leave draining to Nest;
  development still closes connections at once so hot reloads stay fast.

- **ES module apps** could not start: `RenderModule.forRoot()` threw a
  `ReferenceError` from the package's ESM build, and production pages rendered
  without their root layout. Both are fixed.
- **`allowedCookies` without a cookie parser**: cookies were only read from
  `request.cookies`, which exists only with `cookie-parser` or
  `@fastify/cookie`. Without one, `useCookie()` returned nothing. Allowlisted
  cookies are now read from the `Cookie` header when no parser is installed.
- **npm, yarn and bun projects**: `init` wrote pnpm-only `build` and
  `start:dev` scripts. It now writes scripts for your package manager.
- **Server performance**: about 16% less CPU per server-rendered page,
  measured against 0.3.31 in a single interleaved run; output is
  byte-identical except for the JSON fast path (plain hydration state only),
  which changes response bytes but not the hydrated value — see
  [Performance](/performance).
